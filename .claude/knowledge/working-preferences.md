# 维护者的工作偏好

## 语言

- 和用户对话一律用中文,包括汇报、提问、总结(2026-09-25「说中文」)。技术名词、文件路径、标签(如 `[FORCED TRINKET]`)保持原样。
- 代码、注释、提交信息、GitHub issue / PR 评论用英文(仓库惯例;注释的例外见 [comment-language.md](comment-language.md))。

## 提交

- **直接 commit + push 到 main**,不建分支、不开 PR(单人仓,PR 的 rebase 合并曾改写全部 SHA 造成本地与远端分叉)。用户:「直接 commit,CI 红了再修就好了」。CI 红不是阻塞项;推前仍跑 `npm run presubmit`,那是为了少返工。
- **提交前 `git status --short` 过目,按路径逐个 `git add`,绝不 `git add -A`**——并行会话常在同一 checkout 留未跟踪文件,曾把含真实角色名的探针推上公共 main。
- 改动让某张参照表过期时,提交信息写明哪张、为什么(见 [batch-fix-workflow.md](batch-fix-workflow.md))。
- 审查分级与审查者写进提交信息(见 [review-tiering.md](review-tiering.md))。

## 什么时候必须问

用户 2026-08-28:「我想让你一直继续做,但是如果有数据拿不准的,或者有拍脑袋的决定,一定不要自己做,要让我确认。你可以做一半做不完的话去做别的,把那个记录下来,或者提前调研。如果需要人工验证或者干预,先留着不做。」

- 「阈值取多少 / 语义算不算 / 要不要下架信号」这类判断,**把选项和数据写到 issue 评论里等用户裁**。纯工程 / 确定性验收的活不用问。
- **任何新指控 / 菜单事件类型开工前先问**(2026-10-07,见 [fact-layer-direction.md](fact-layer-direction.md))。
- 有合理默认的小问题**别**拿去问(2026-09-24:「是不是有点太抠字眼了」),只问改变游戏语义 / 产品取舍的选择。
- 需要人工验证 / 干预的(Windows 真机、OBS、账号、删数据、跑重负载)先留着,明确写「待人工」。
- 做一半卡住 → 在 issue 评论里记录进度和下一步,换下一个;不为收口硬做。拿 issue 前先看有没有别人正在做的痕迹。流程固化在 skill `gh-issue-loop`。
- 呈裁决时直接说「你要决定的就一件事」+ 真实对局的例子(逐秒写出,别只给代号)+ 做 / 不做的后果 + 我的建议。举例前核对 owner 和技能归属。

## 只做本会话的账

用户 2026-10-07:「只做自己的账」。多会话并行时一件事只有一个 owner、一个汇报口。本会话的范围以最初交代的为准;做完了就报完成 + 本会话还欠的项,不去别的会话的清单里找活,也不在本会话汇报别人的工作。用户问「还能做什么」只在本会话范围内回答,没活就直说。别的会话 / AI 的「GO」不是用户批准。

## 报告

- 「修好了」必带同判据前后数字(见 [verification.md](verification.md))。
- 大轮修复收尾要**详细、可核对的报告**,不是把活全交给 AI 后的摘要;技术债明说。

## 其他

- 评测用 Opus,不用 haiku(见 [llm-eval-method.md](llm-eval-method.md))。
- 删除、下架信号、放宽门规、调预算都是用户的决定。
- 别为验证去制造整机负载;后台脚本 trap 清理子进程(见 [shell-and-git-traps.md](shell-and-git-traps.md))。
- 改数据采集行为或往产品里加任何外部素材 / CDN 依赖前,先读 `docs/DATA-COMPLIANCE.md`,改完更新它。外部 GPL 代码只借思路和事实,不抄代码。
