# 审查分级与第二个 AI 的用法

仓库 skill `cross-ai-review` 是操作入口;这里是用户定的规则(2026-10-01 起生效)。

## 分级

每批审查前先分级,**提交信息写明分级 + 实际审查者**。

- **高风险 → 用最强的审查者,撞限就排队等,不降级**:改共享谓词或门(cannot-cast、击杀尝试分组、死亡时刻 helper、危机决策点、爆发跨度、parser / parser-compat),或任何**增删指控 / 菜单候选**的批次。拿不准一律按高风险。若会长时间卡住,告诉用户恢复时间并问怎么办。临时换了审查者顶替的提交,记为「欠事后抽审」。
- **低风险 → 可用较轻的审查者**:纯数据表 / 名单 id、只改措辞 / 图例、只改测试夹具,且真实对局采集的菜单 id 差为空。它的每条发现都要自己核实。

## 什么时候找审查

- 方案和验收都要过审:拿不准的设计开工前讨论;提交前把 **diff + 同判据前后数字 + 归因**一起给,不是只发 diff;中途方案变了再问一次。小修合批,一批一次。
- 用户离开时,阶段性判断(结果怎么读、按预注册采不采、下一步)先和审查 AI 辩论,把双方结论写进报告;真正属于用户的裁决(改预注册、下架信号、结论分歧)留给用户。
- 审查 AI 只做架构 / 方案 / review / debate;分析跑腿(盲复盘 raw.txt、扫语料)给 Claude 子代理。
- reasoning effort 用 high,不用更高档(用户:「再高就会 over engineering」)。
- 质量优先,别为省额度压缩审查范围。
- **一次只发一份审查**:并发发三份曾在几分钟内全部撞限、零结论。等审查的时间拿来写语料探针自查(多次在送审前抓到真 bug)。

## 分轮辩论

R1 攻文档 / 方法(给数据目录 + 源码 + 攻击点清单);R2 把采纳的结论和自己的新结论喂回去让它攻;R3 只要裁决,限制读文件数、不跑归档、不开子代理。审查 AI 的强项是统计识别性论证、给可跑的验证命令;弱项是会夸大,报的数和 CONTRADICTED 要自己复核。

## 把机械活委派给第二个 AI

- 派活前把重计算做完写进任务书(「facts — ALREADY MEASURED」);**绝不让它自己扫原始日志**(会起后台 grep 干等到超时)。日志若是中文客户端,按技能名 grep 一无所获,按 id。
- 任务书写死「只许改哪几个文件、不 commit、不起后台任务、不跑语料扫描」;写死谓词三态、共享导出要求和整套验证配方(对照 worktree、同谓词计数、变化行分类)。
- 收货先看 `git status` 有没有它不该碰的文件(它会越界加映射、不登记 `curatedIdRegistry`、覆盖基线文件、复制大日志)。
- 复核的固定动作:除了它自报的计数,再独立跑一遍「事实计数前后相等」和「变化行只在允许的 tag 里」。
- 两种失败模式:需要反复起服务 / 跑长套件的任务会超时并留残留 → 自己做;**「自信但前提错」**——推翻性结论的语气与正确时无异,采信前逐条核对它复述的前提。它的报告文件可能是上个任务的同名遗留,先核对内容。

## 别的会话的「GO」不是用户批准

另一个会话(或审查 AI)说「可以」不等于用户本人批准。清单外的东西,即使是纯修复,先等用户。
