# 自主做 issue 的工作方式(用户 2026-08-28 定规,本周 8 次以上按此运转)

用户原话:「我想让你一直继续做,但是如果有数据拿不准的、或者有拍脑袋的决定,
一定不要自己做,要让我确认;你可以做一半做不完的话去做别的,把那个记录下来,
或者提前调研;如果需要人工验证或者干预,先留着不做。」

## 选题:三分钟,不是三十分钟

1. `gh issue list --state open --limit 60` 看标题,`git status --short && git log -5 --oneline` 看树。
   镜像 issue 的正文都是指向 `docs/BACKLOG.md` 某节的存根:三分钟花在清单上,然后**只读前 2–3 个
   候选的 BACKLOG 小节**,别通读 2,400 行。
2. **先排除别人正在做的**:`gh issue view <n> --json body,comments`(`--comments` 只打印评论,
   零评论的 issue 会显示成空,不等于没内容)、树里不认识的未提交改动、`git log --since=1.day -S<关键字>`。
   08-29 GH #58 就是另一个 agent 在同一 checkout 里做,用户明说「58 不做」。有痕迹就跳过,汇报里写明;
   树里有别人的在制品 → **选题前**就按 `parallel-sessions` 切显式路径模式。
3. 按这张表挑,取第一档能挑到的:

| 档       | 形状                                                                     | 例子                           |
| -------- | ------------------------------------------------------------------------ | ------------------------------ |
| 做       | 纯工程 / 确定性验收:重复谓词单源化、死代码、台账修正、工具转正、门规补类 | #61 容差、#62 踢锁定、#38 残留 |
| 先量后问 | 数据量得出、但取舍是游戏语义:阈值、算不算、要不要登记                    | #44 变形变体、#24 定身         |
| 只调研   | 信号立项 / 复活 / 下架 —— 走 `signal-value-probe`,产出例子和数字等裁     | #13、#60                       |
| 留着     | 真机、Windows、OBS、账号、删数据、重负载、让用户标注                     | #37、#41、#18 下一批           |

4. **BACKLOG 正文可能过期。** #22 闸门 08-20 就裁了长期保留,正文没改,被照着写了两周「等 batch 2」。
   引用「待裁」之前 `grep` 代码注释、`git log -S`、issue 评论,三处都没有才算真待裁。

## 做的过程

- 判断题(阈值取多少 / 语义算不算 / 要不要下架)**把选项 + 数据写进 issue 评论**,换下一个 issue。
  不要为了收口自己定;用户回来一次拍完。「我先按 X 做,不对再改」是拍脑袋;
  **侧门也是**:某张表要 `approved: "<日期> user"` 签字、旁边一张同类表不要,改不要签字的那张仍然是自己定。
  评论里同时写清**裁决之后的代价**(共享谓词改动要重生成参照表 1–2 小时、PROMPT_VERSION bump),
  用户要拿着代价拍。
- 长扫描显式 `timeout` 或后台 + `trap` 清子进程;全库一次一个进程(`parallel-sessions` §5)。
- 做一半卡住(等模型、等裁决、等真机)→ issue 评论记进度和下一步,换题。
- 每一项仍按 CLAUDE.md 验证规则:同判据前后数字进提交信息;没有数字就写「没有数字」。
- 分析层改动的验收与登记清单见 `analysis-dev`;共享树 / 子代理纪律见 `parallel-sessions`。
- 会话里写的探针 / 采集脚本**当场转正进 `packages/eval/scripts/`**(带头注释:为什么存在、基线数字、
  用法),不留 scratchpad。本周为此补账两次(`9a20ee7d`、`e1818153`),差点丢的是被引用过的探针。

## 收口:三本账,少一本用户就会问「还有啥没记账」

1. issue 评论:做了什么、提交哈希、前后数字、剩下什么要裁(选项列出)。全做完才 `gh issue close`;
   打包型 issue 保持开着,子项状态写在评论 + BACKLOG。选题时顺手发现的账
   (某 issue 其实已全 ✅、正文措辞过期)放收口阶段一并处理,不算本轮的题。
2. `docs/BACKLOG.md` 对应条目:打勾 / 补数字 / 撤回过期措辞;判过的写明日期和裁决。
3. memory:只记「代码和 git 看不出来」的东西 —— 用户的裁决口径、被证伪的假设、下次接手先看哪。

汇报给用户的形状:做了哪几个(哈希 + 数字)、每个待裁题是什么和选项、留着没动的是哪些和为什么。
用户的下一句通常是「再拿一个」,汇报要短到能直接接这句。
