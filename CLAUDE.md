# gladlog

## Shared-Predicate Rule

Analysis code (`packages/analysis`) and verification gates (`packages/eval`'s positioningScan/qualityCheck/layerA audit) must share **the same predicate** for **the same fact** (HP, distance, LoS, timestamp): same constant, same sampling function, same tolerance, and **anchored to the rendered value** — the prompt renders `fmtTime` (floor to whole seconds), and the gate re-parses the rendered text, so fractional seconds / raw timestamps inside analysis must be floored to the rendering grid before any gate-recalculated check.

Historical cost of violating this rule: in the 2026-07 full audit, 5 independent bugs were all of this class (HP sample radius inconsistency, bounded vs unbounded lookback, interpolated vs raw vs non-simultaneous sampling for LoS, fractional-second vs rendered-second scan grid). The fix is always to make analysis consume the gate's predicate, never to relax the gate. Sharing-point examples: `cooldowns.ts`'s `HP_SAMPLE_RADIUS_MS`; `positionSampling.ts`'s `LOS_SWEEP_SLACK_S`/`LOS_SWEEP_GAP_MS` — `positioningScan.ts`'s `TIME_SLACK_SECONDS`/`POSITION_MAX_GAP_MS` are now direct aliases of these (structural coupling, harder than "must be equal"). Note the two examples have **different structures**: in the first, the gate side has no corresponding constant at all and verifies by re-parsing the already-rendered prompt text — "shared predicate" doesn't always mean "shared constant".

When adding any new "analysis asserts X, gate verifies X" pair: export the predicate from one place, import on both sides; if that's not possible, write a unit test asserting equality — don't rely on comments.

**Where existing predicates live: see [`docs/predicate-index.md`](docs/predicate-index.md)** (170 entries plus a 15-row feature-flag ledger, with a consistency test in `packages/eval/test/predicateIndex.test.ts`: renaming/moving a symbol turns CI red). The index doesn't only track analysis↔gate pairs: since 2026-08-04 it also tracks cases within the desktop renderer where **two consumers** check the same fact (the "Report UI" section), with the same criterion of "one fact, one predicate". Check the table before writing new code — the rule has never been lacking; what was lacking was the index: on 2026-08-01 someone read this section and still hand-copied two predicates that same day. When the index went live, it immediately caught 5 registered violations, **all closed on the same day** (4 converted to shared exports, 1 confirmed to not be a duplicate); register newly discovered duplicates in the doc's "Not yet unified" section. That section is **not** empty and is not supposed to be: as of 2026-09-02 it carries zero open divergences (the 2026-09-01 one — the two disjoint offensive-cooldown id tables, GH #60 coarse spot 4 — was closed via the canonical `OFFENSIVE_CD_SPELL_IDS` on 2026-09-02; the one before it — `uwcCorpusScan` reading `DR_CATEGORIES_GENERATED` raw while the product goes through `DR_CATEGORY_MAP`'s override layer, disagreeing on 33786 Cyclone and 99 Incapacitating Roar — was closed via `drCategoryIds` on 2026-08-27, GH #33) plus two entries recorded as _deliberately_ not shared, so nobody "unifies" them by mistake. Read it before concluding a duplicate is new.

## Verification Rule

When claiming a bug is "fixed", include **before/after numbers under the same criterion** (e.g. "type-A same-second HP contradiction 26/50 matches → 0/50").
If you can't provide numbers, say so explicitly — **reading the code + writing a convincing commit message does not count as verification**.

The 2026-07-20 cost: `3cd5342` fixed same-second HP contradiction by "unifying HP sample radius"; the root-cause explanation was perfectly plausible and it landed on main; later testing showed **26/50 → 26/50, not a single number moved** (the radius only controls accept/reject, it doesn't change the sampled value; the real root cause was the query timestamp not being on the rendering grid). On the same day, `dbe61bd` **extrapolated from a single sample to the entire class**, misclassifying type-D as "marker ambiguity"; an independent reviewer disproved it with a counterexample (`c820ad4`).

Complementary practice: prefer making criteria into **deterministic text checks baked into the gates** (`packages/eval/src/quality/promptQualityCheck.ts`'s `hardFailures`, currently fifteen classes: friendly death coverage / percentile monotonicity / same-second HP consistency / window duration self-consistency / cooldown ledger consistency / snapshot facts consistency `checkSnapshotFactsConsistency` / self-only defensive claims `checkSelfOnlyDefensiveClaims` / DMG-SPIKE CC-cover cross-reference `checkDmgSpikeCcCoverConsistency` / DMG-SPIKE `healed through` ⟺ same-line HP delta `checkHealedThroughConsistency` / behavior-prior reference consistency `checkBehaviorPriorConsistency` / crisis-HP ⟺ same-second `[STATE]` tick `checkCrisisHpStateConsistency` / corpus outcome-reference consistency `checkOutcomeRefConsistency` / candidate-menu time-fact render-grid consistency `checkMenuTRenderGrid` / burst-window reference consistency `checkBurstWindowRefConsistency` / sync-window reference consistency `checkSyncWindowRefConsistency`) — don't leave one-off scripts; they vanish with the session and no one blocks the next regression.

## Curated-List Completeness Rule

Whenever official data is reached **through a hand-maintained list** — a candidate/allowlist/tracking set that decides _which ids the official lookup even runs on_ — that list is part of the predicate, and its **completeness** must be verified separately from its correctness. Verifying only "is every entry in the list right" proves there are no false positives; it can never prove there are no false negatives.

This has now bitten five times, always the same shape (the list silently swallows official data, and the failure looks exactly like "the game doesn't have that"):

- **2026-07-25**: `DISPEL_TYPE_FALLBACK` was emptied after an audit confirmed all 8 hand entries were bogus, concluding "the official dispelType is the complete predicate". It checked only the entries present.
- **2026-08-13**: the list need not gate the _lookup_ to do this — it can gate the **verdict**. `getDispelType` is clean (official DB2, hand fallback emptied 2026-07-25), but `dispelAnalysis.getPriority` recognises a buff only via two hand lists (the mitigation allow-list → Critical, `spellCategories` 94 entries → High/Medium); anything unlisted is Low, and the missed-dispel analysis only collects Critical/High. **Not listed = permanently invisible**, and it looks exactly like "there was nothing worth dispelling". Measured: 72 corpus buffs that are officially dispellable were being scored Low — Ice Barrier is the clean example (official Magic type, simply no category entry).
- **2026-08-17**: `collectCandidateIds` (8 sources, all hand-maintained) gates which ids enter `spellEffectGenerated.json`, which is what `getDispelType` reads — so a debuff nobody had listed could never be _known_ dispellable. Measured: **145 spells / 76.5% of all corpus dispels** had no entry at all (Shadow Word: Pain, Moonfire, Corruption, Vampiric Touch…).
- **2026-08-18**: `genTalentModifiers`'s step-6 "sanity filter" gates on `trackedSpellIds` (same kind of hand list), discarding correctly-mined talent cooldown/charge modifiers for any unlisted spell.

- **2026-08-18** (GH #23), the worst shape so far — **not incomplete, entirely stale**: `DISPEL_PENALTY_SPELLS` (the "don't cleanse it, it backlashes" exemption) knew Unstable Affliction only as `316099`/`342938`, which occur **zero** times in 1178 rounds, while the live `1259790` (1153 applications, 519 dispels) was unlisted. 100% of the list dead, 100% of real exposure unlisted. **Two tells worth memorising**: (a) the comment dated itself — "confirmed present in BigDebuffs data for TWW", and TWW is the _previous_ expansion, so a spell renumber had silently emptied the list; (b) `dispelPenalty.test.ts` **predicted this exact failure** ("the moment a DB2 refresh fills in UA's dispelType, false reports appear immediately") and still missed it, because it pinned the dead id — a test that pins the wrong key is worse than no test, it manufactures confidence. Only UA's unrelated `Low` priority was suppressing the false accusations.

**The check to run**: take the observable ground truth (corpus events — `SPELL_DISPEL`'s own `extraSpellId`, observed casts, …) and ask which ids the official path fails to explain. `packages/analysis/src/data/observedSpellIdsGenerated.json` exists precisely for this and should be a source in any such list.

**Run it in both directions.** The check above finds ids the list is missing; the cheap reverse pass finds ids the list has _gone stale on_ — intersect the list's own keys with `observedSpellIdsGenerated.json` and look at what has **zero** corpus occurrences. Every entry a patch renumbered shows up immediately, and it costs one set intersection. Spell ids are not stable across expansions: an id that was right when written stays in the file looking authoritative forever.

**Both directions are now tooling, not a manual chore — and every hand list must register itself.** `packages/analysis/src/data/curatedIdRegistry.ts` is the roster of hand-maintained id tables (61 registered); a new table that is not registered there is invisible to the scans, which reproduces the very failure this rule exists to catch, so **registering is part of adding the table**. The scans: `curatedRotScan` (reverse — registered entries with zero corpus occurrences), `drGapScan` (forward — observed CC the DR tables cannot explain), `dispelCompletenessScan` (forward — `SPELL_DISPEL` the official path cannot explain). Runbook and the season cadence: [`docs/commands/update-wow-data.md`](docs/commands/update-wow-data.md) §7b. The 2026-08-21 12.1 health check that these produced is the worked example: 44% of the season's observed ids were outside the universe, 155 registered entries had zero occurrences, 14 wrong ids and 22 deleted spells were cleared out of 19 tables.

Corollary: **when you change what a predicate keys on, re-verify every property its comments claim.** `TALENT_BEHAVIORS`' "self-gating — the aura only exists when the talent is taken" was true while availability keyed on the _buff's_ own casts, and false the moment it keyed on the _trigger_ ability (Fade / Psychic Scream exist for every priest). Measured cost before the talent gate was restored: 303 of the proc tools' citations belonged to players who had not taken the talent.

## Game-Behaviour Rule (hand tables that assert what the game does)

The rule above governs which ids a list _contains_. This one governs what a list _claims about the game_ — a duration, a modifier, a proc. Those claims rot on a patch cycle and are wrong in ways that look exactly like correct data, so they need a stricter evidence bar and a re-runnable check. Every lesson below was paid for on 2026-09-06/07 while building `BUFF_DURATION_TALENT_MODIFIERS`; the table's own header carries the worked examples.

1. **Three-way evidence, and the mask is the load-bearing third.** A talent modifier needs (a) the DB2 row, (b) **its `SpellClassOptions` mask actually covering the target spell**, and (c) a corpus split, with (d) the arithmetic reconciling. Skipping (b) produced 23 "matches" of which most were nonsense — Tiger's Fury attributed to Improved Barkskin — because a talent held by ~100 % of a class carries no discriminating power. Adding it cut the list to 10 and killed exactly the two a human had flagged by eye.
2. **Ask DB2 first, use the corpus to choose — not to nominate.** "Which modifiers' masks can legally reach this spell" is a complete list and usually has fewer than ten rows. Nominating from the corpus instead hid Hover ← Extended Flight and Recklessness ← Rampaging Berserker for two rounds.
3. **Never require the control group to lack the talent.** That filter silently discards every universally-taken talent, which is most of the interesting ones (Improved Barkskin sits on ~100 % of druids; its "control group" is 2 casters out of 280).
4. **Read ranks from COMBATANT_INFO; never infer them from the arithmetic.** DB2's per-rank vs total-at-max-rank is NOT uniform across talents — Timeless Magic is per rank, Divine Wrath / Extended Flight / Rampaging Berserker are totals. Three entries shipped wrong by a factor of two within the hour because the rank was inferred from a number that happened to fit.
5. **Run the arithmetic against the DB2 base, not the hand override.** The override may be neither the base nor the talented value (Recklessness' hand 16 against a DB2 12 and an observed 18), and it will make a solvable case look unexplainable.
6. **Before calling a mismatch unexplained, count the casts.** An aura produced by a proc carries the trigger's duration, not its own (Ascendance: 18 casts against 1,684 applications, all Deeply Rooted Elements). And an aura id that is never cast at all is usually applied by a DIFFERENT ability, whose parameters set the length (Rend comes from Thunder Clap 60 % of the time).
7. **Direction is a safety argument.** An aura cannot outlive its duration, so an observation LONGER than the table cannot be an early-removal artifact; a shorter one can (dispel, death, consumption, an interrupted channel). Patch upward on corpus evidence, never downward without a mechanism. Control keeps its official number regardless — user ruling, see `ccFullDurationSeconds`.
8. **It has to be re-runnable.** `packages/eval/scripts/buffDurationScan.ts` re-measures both tables against a season's corpus (ROT = a registered entry no longer reproduces; GAP = an unregistered aura that disagrees) and is in the season runbook, `docs/commands/update-wow-data.md` §7b. Its first run on an unused sample caught three registered entries, two of which resolved immediately — finding leads from the deviation is much cheaper than hunting evidence per entry by hand. Known-open deviations stay FLAGged and are documented in the entry's note; they are never suppressed.

## Value-Gate Rule (new coaching signals)

Every rule above guards whether a number is _correct_. None of them asks whether the thing is _worth existing_, and the higher the engineering quality, the more expensive that gap gets. On 2026-08-16 two mana candidates went through implementation → calibration → A/B with every number recomputed and correct; the user killed both on sight of **one** real output example ("you used too much mana here", detached from whether the enemy burst forced it). Half a day of calibration and batched model calls burned on something refutable in ten seconds.

**1. Value gate before engineering gate.** For any new signal/candidate, the first step after it runs is to produce a **complete real-match output example** and show it. No calibration, no A/B, no batched model calls until that is approved. (The P1/P2 round did this — match `60ab` at 7:19 — and it worked; the mana round skipped it.)

**2. Attribution-shaped work is written backwards.** Hand-write the target conclusion sentence first ("if this were good, what would it say about this real match?"), get it approved, _then_ build the smallest engine that produces it. Do not build the pipeline first and hope intelligence appears at the end.

**3. Feasibility gate — "could the player actually have done it at that moment?"** A candidate builder that only checks "a good thing did not happen" is accusing people of not being psychic. Standing review question for every new type: was the resource ready, was the thing reactable, was the target reachable? Measured: `cc-avoidable` was accusing instant-cast CC 75% of the time (gate → −68%); `unsynced-burst` blames desync when **0%** of accused rounds never CC'd the healer at all. The discipline already existed — the dispel family (GH #20) does all three checks; copy `missedPurgeEvents`. Process item tracked as `docs/BACKLOG.md` #34(b).

**4. Discrimination must be opportunity-normalised before it means anything.** Occurrence rate (win-trigger% − loss-trigger%) is confounded whenever the _opportunity_ correlates with winning, and it then points the wrong way. GH #13: occurrence discrimination −4.4pp ("triggers more when winning" ⇒ looks harmful), but wins had 8.30 opportunity windows per match vs 7.19 for losses, and the **conversion rate was flat (26.7% vs 27.8%)** — the behaviour is unrelated to the outcome. Always ask what the denominator is before reading the sign.

**5. Win/loss is a circular axis; rating bracket is external truth — and this corpus must be stratified before it is compared.** Round events cannot manufacture the player's rating; they can manufacture the outcome (a stronger opponent both controls you more _and_ beats you). Pooling across brackets fabricates effects outright: `death-unused-defensive` shows a clean monotone −9.6pp pooled and **+0.1pp** inside Solo Shuffle alone, because bracket composition shifts with rating (<1600 is 63% Solo Shuffle, 2400+ is 91%). `aggregateGradient` refuses a pooled call and a unit test pins it.

**6. Two judge dimensions cannot adjudicate an A/B.** `accuracy` has a paired noise floor of SD ≈ 1.3 (|Δ| < 0.4 is unmeasurable) and `sufficiency` detects planted defects 20% of the time. Fixes to prompt-internal consistency are adopted **on deterministic evidence**, stated as such — never dressed up as a blind-A/B win.

Evidence base for all six: [`docs/coaching-grounding-audit.md`](docs/coaching-grounding-audit.md) (per-signal grounding provenance) and `docs/BACKLOG.md` #34 (the skill-gradient experiment's open rulings). Retiring a signal is a user call, not an aggregate-number call.

## Bilingual Docs Rule

The following 12 documents have **English as the canonical version with a `.zh-CN` suffix for Chinese**; both versions must be equivalent — update one side, update the other, or don't update at all:

`README.md` · `CHANGELOG.md` · `docs/user-guide.md` · `docs/FAQ.md` ·
`docs/setup-windows-claude-cli.md` · `docs/developer-guide.md` ·
`docs/BUILD-WINDOWS.md` · `docs/verifiability-roadmap.md` ·
`docs/DATA-COMPLIANCE.md` · `docs/pvp-log-archive.md` ·
`docs/architecture.md` · `docs/predicate-index.md`

**Package-level READMEs follow the same rule**: wherever `packages/<pkg>/README.zh-CN.md` exists, `README.md` is the canonical version and both must be equivalent (currently: `analysis`, `desktop`, `corpus-tools` — the last converted from its Chinese-only single version on 2026-08-21).

Each document has a language bar on the line immediately below the H1 heading (current language bolded without a link, the other language as a link); cross-links stay **within the same language** — English docs point to English files, Chinese docs point to `.zh-CN.md` files, never cross-language. New user-facing docs follow this pattern as well.

## Common Commands

- Type check: `npm run typecheck` (never `tsc -b` — it emits .js files into src).
- Before pushing: `npm run presubmit` (= `eslint .` + typecheck + **all-workspace** tests + `verify:vision` + `electron-vite build`). It is the union of the CI `test` workflow's `static` and `unit` jobs (CI fans the unit tests out across parallel runners; `frontend-qa` is separate and never run locally). Do **not** hand-type the old three-piece (`npm test --workspace=packages/desktop && npm run typecheck && npx eslint .`): it skips `verify:vision` and the production build, and the build step is the only local thing that catches a renderer value-importing `src/main/*` — dev and vitest both let that through until the packaged app dies. Two scope traps behind it: lint must be `eslint .` from the **repo root** (a `cd` into a package silently narrows it and CI goes red — three consecutive failures), and tests must be all-workspace (analysis/parser cases run in CI too). Locally, `npm test` in `analysis` / `eval` shares the module cache for files listed in their `vitest.shared.json` (fail-closed: new test files run isolated until listed; CI is always fully isolated; `GLADLOG_TEST_ISOLATE=all` forces full isolation when a failure might be a state leak) — see `docs/developer-guide.md`. Engineering conventions are in `.claude/skills/desktop-dev` (desktop) and `.claude/skills/analysis-dev` (analysis package). New / resurrected / retired coaching signals go through `.claude/skills/signal-value-probe`; autonomous issue work through `.claude/skills/gh-issue-loop`.
- Eval workflow: `/eval-baseline` (find issues) → `/eval-ab` (verify fixes) → `/calibrate-judge` (calibrate scoring) → `/pipeline-audit` (full-corpus audit). Artifacts go in `$GLADLOG_EVAL_HOME` (default `~/code/gladlog-eval-private`).
