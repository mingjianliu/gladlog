## 三、还开着的活(按杠杆排序)

### 1. ~~给 finding 加「这条是错的」反馈~~ —— **2026-08-17 用户决定暂不做,别再捡起来**

调查做过了,结论记在这里,免得下一个人重做:

**现有管线用不了。** `packages/log-pipeline` 不进安装包(`packages/desktop/package.json` 不依赖它,只从 corpus-tools 拷了一个 `reference_vectors.json` 作 extraResource),它是维护者两端手动跑的字节精确日志中继,不是产品功能。已发布 app **唯一**的出站能力是 `electron-updater` 的 `provider: "github"` 单向 GET —— 没有 POST、没有遥测、没有任何 `fetch`。要把反馈送出去是从零新建通路。

**但这个问题本来该拆成两半,两半的答案不同:**

- **(a) 项目所有者自己的反馈根本不需要管线。** 他在 Mac 上看报告(1029 场库和分析缓存都在 Mac 上),标记天然落在开发机。而审计的结论正是「缺的权威就是他的判断」—— 一个人的金标就够启动(参照:减伤问卷 32 条十分钟填完,直接变成签字常量表)。
- **(b) 其他用户的反馈是另一个项目,价值存疑。** 规模实测:v0.1.26 有 43 次下载、v0.1.25 有 24 次,GitHub 上 1 个外部 issue 提交者(`liuxinlei` #4),几十人量级。要做得付出:新建出站通路 + 知情同意 + 合规(`DATA-COMPLIANCE.md` 现有那套讲的是**上传者已同意公开**的第三方日志,收集自己用户的数据是完全不同的处境)。而且他们不是冠军级玩家 —— 他们的「这条不对」可能只是不认同,是噪声。

**如果将来重启这条,有一个设计要点能让它便宜很多**:payload 不要放 finding 正文,只放 `{候选类型, 错误分类, promptVersion, 版本号}` —— 不含角色名,零个人数据,合规从「处理伪匿名个人数据」降级为「只需一个 opt-in」。到那时最省事的通路多半也不是自建服务,而是让 app 拼一个预填好的 GitHub issue 链接在浏览器打开:零后端、零凭据、用户看得见发出去的每个字。

**三分类的设计仍然有效,留档备用**:反馈不该只有一个「错」,而该分三类 —— 事实就是错的(去修检测器)/ 事实对但不是失误(去修判据条件)/ 是失误但这是废话(该下架这个类型)。三者对应三种完全不同的修法,而 `eventIds` 前缀自带候选类型,按类型聚合是免费的。

## 四、工作方式(这轮踩出来的)

**验收必须有前后数字,同一判据。** 推荐的脚手架:临时脚本放 `packages/eval/scripts/zz-tmp-*.ts`(跑完即删),用 `packages/eval/src/explore/storeAccess` 的 `loadIndex`/`pickRows`/`loadLegacyRound` 遍历本机库,**同时输出 prompt SHA256 + 逐类候选计数**。只看 prompt 哈希不够——本轮 HP 半径那条正是靠候选计数全等才敢说「不改任何教练判断」。改动前 `git stash` 再跑一次对比。

**加守卫必须做负控。** 证明它会红,再证明恢复后会绿。本轮两次(开关断言、裁定册漏项检测)都这么做的,而且都在第一次就抓出了真问题。

**别发明数字。** 这是整份审计的中心结论。要么接官方数据,要么接语料实测,要么让用户签字。三条都做不到就记成 `unresolved` 不出面——项目已有先例(`PURGE_WHITELIST_DATA_BLOCKED`、feared 维度)。

**跨 AI 复核。** 非平凡改动推之前走 `agy`(skill 名 `agy`)。本轮它推翻了我两个方案(注册表拆分、experiments 目录),而且都是对的——它的反驳要当真,但也要自己核它引的 file:line,它也错过(它说 `deathOutcomeAnalysis` 的表混装,实际那是按「自救 vs 外置」分的,分类没错)。

**提交方式**:直接 commit + push 到 main,不建分支不开 PR,CI 红了再修。

**空对照阶梯 —— 判别力提升必须先减掉「上下文本身」。**

给一个信号加上下文门之后判别力上升,**不能直接当成功**。要先量一个阶梯:门本身单独有多少判别力(不看信号内容)、信号本身单独有多少、以及**同上下文但玩家行为相反**的对照。

实例(#16 的 G2 脆弱窗门):表面 +3.2pp → +12.6pp,像是翻了四倍。阶梯拆开后:

- N0「任何脆弱窗存在」= **−0.9pp**(门本身零判别力,不是循环论证)
- N3「窗内上身**且被驱掉了**」= **−1.6pp**(同上下文、行为相反 → 信号消失,这条最关键)
- N4「窗内上身,不论驱否」= **+7.7pp**(敌人挑没墙的队友下控,**玩家控制不了**)
- S1 完整信号 = +12.6pp

**可教增量 = 12.6 − 7.7 = +4.9pp**,不是 +12.6。判定规则要**事先写进脚本**,别出了数字再挑口径。

**重扫描一次只跑一个。** 本机全库扫描(1028 场 raw.txt / 1178 回合)吃内存,并行两三个 tsx 进程差点 OOM。验收/探针一个一个来,别图快。

## 六、给用户提问的方式

用户是奶主玩家、领域专家,**他的判断就是这套系统缺的那个权威**。本轮最有效的一次交互是做了个网页问卷让他逐条裁定(artifact `63e64c88`),32 条十分钟填完,产出直接变成签字常量表。

要点:**预填你的猜测让他改,别让他从零填**;**把语料证据摆在每条旁边**(施放次数、现在代码怎么判的),他能一眼看出哪些是「我没遇到过」哪些是「真没了」;**允许他答「这条无效」**——本轮两条未决正是这么来的,而那恰恰是正确处理。

还有一条:他说「这个很难量化」的时候,往往意味着**该去语料里测,而不是让他猜**。本轮 `KILL_LIVE_HP_PCT` 就是这么定的——他说难量化,我去测了 900 个单位的击杀转化率,他看着曲线签了 20。
